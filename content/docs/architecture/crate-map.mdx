The workspace has 64 crates under `crates/`, plus the `xtask` gate runner. 53 of them are published
to crates.io at version 0.1.0; the other 11 are tooling or the experimental Linux console stack. An
application depends on `zgui` and usually nothing else (see
[What an application depends on](#what-an-application-depends-on)).

## Layers

Every crate belongs to one of nine layers, from L0 (foundation) to L8 (product).
[The architecture overview](/docs/architecture/overview) describes what each layer holds. **A crate
may depend on crates in its own layer or a lower one, never on a crate in a higher layer.**

Each manifest declares its layer in a comment above `[dependencies]`:

```toml title="crates/zgui-layout/Cargo.toml"
[package]
name = "zgui-layout"
version.workspace = true
edition.workspace = true
# ... the other shared package keys

# L4 — engines. Every dependency is inherited: `foo.workspace = true`.
[dependencies]
zgui-css = { path = "../zgui-css", version = "0.1.0" }
cephal.workspace = true
```

`cargo xtask new-crate <name> --layer L4` writes such a manifest and a crate root with
`#![deny(missing_docs)]` and `#![forbid(unsafe_code)]`. It accepts `L0` to `L8` only.

The rule keeps each part replaceable and testable on its own:

- **A backend upgrade reaches one crate.** A breaking winit release touches `zgui-platform-winit`
  and nothing else.
- **Every stage is testable without the one below it.** The style engine runs without layout,
  layout runs with fixed-metrics text and no fonts, paint runs without a GPU, and the frame loop
  runs without a display server.
- **A second implementation is not a fork.** There are four platform backends, two vector
  rasterisers, two text metric sources, and a capture renderer beside the real one.

### When a dependency would point upward

A stage that needs a fact from a higher stage must be handed it. Use one of three moves:

1. **Invert the dependency.** The lower crate declares a trait; the higher crate implements it and
   passes it in.
2. **Push the type down.** `zgui-vocab` exists for this.
3. **Add a facade.** `zgui-css` is the facade for the style engine.

A feature flag that enables an upward edge does not help: the [`layers` check](#layers-check) reads
normal and build dependencies, optional or not.

## What an application depends on

An application names `zgui`. The examples package shows this: every example depends on `zgui` only.
There are three exceptions:

| Crate | When an application names it |
|---|---|
| `zgui-image` | To register encoded image bytes from memory (`ImageBytes`). File paths need only `zgui`. |
| `zgui-devtools` | To mount the inspector. `zgui` does not re-export it, so a release build does not link it by accident. |
| `zgui-console` | To run on a Linux console with `run_drm`. Not published. |

Test crates name `zgui-testkit-view`, `zgui-testkit-scene` or `zgui-platform-headless` in
`[dev-dependencies]`. None of them is re-exported by `zgui`.

The component library follows the same rule: `zgui-ui-tokens`, `zgui-ui-icons` and
`zgui-ui-primitives` depend on `zgui` only, and `zgui-ui` depends on those three and `zgui`.

`crates/zgui/src/lib.rs` re-exports the lower crates under short names:

```rust title="crates/zgui/src/lib.rs"
pub use crate::app::{App, app};
pub use crate::error::Error;

pub use zgui_view_macro::{component, css, slot, style, variants, view};
pub use zgui_elements::expansion;

pub use zgui_atlas as atlas;
pub use zgui_bits as bits;
pub use zgui_canvas as canvas;
pub use zgui_custom as custom;
pub use zgui_elements as elements;
pub mod desktop {
    pub use zgui_platform::{AppMenu, MenuAction, MenuEntry, MenuId, MenuRole, Shortcut, Submenu};
    pub use zgui_runtime::desktop::{AppHookGuard, on_exit, on_menu, on_reopen};
}
pub use zgui_geom as geom;
pub use zgui_platform as platform;
pub use zgui_reactive as reactive;
pub use zgui_reactive::task;
pub use zgui_render as render;
pub use zgui_runtime as runtime;
pub use zgui_scene as scene;
pub use zgui_shader as shader;
pub use zgui_text as text;
#[cfg(feature = "tokio")]
pub use zgui_tokio as tokio;
pub use zgui_view as view;
pub use zgui_vocab as vocab;
pub use zgui_wgpu as surface;
```

### `zgui::expansion`

`view!` expands to calls into `zgui-view` and `zgui-elements`. A macro cannot know what the caller
named those crates, so the expansion always goes through `::zgui::expansion::view::…` and
`::zgui::expansion::elements::…`. That lets a crate that writes views depend on `zgui` alone.

A crate that writes views without `zgui` supplies the root itself:

```rust
extern crate zgui_elements as zgui;
```

## Replacing a backend

| Replace | Depend on | Implement | Install with |
|---|---|---|---|
| The renderer | `zgui-render` | `Renderer` | `App::with_renderer`, which takes a `zgui_runtime::RendererFactory` |
| The vector rasteriser | `zgui-render`, `zgui-render-wgpu` | `VectorRaster`, `zgui_render_wgpu::VectorSource` | `WgpuRenderer::set_vector_factory_for`, usually through `zgui_render_vector_vello::attach` |
| The platform | `zgui-platform` | `PlatformCx`, `Surface`, `Clock`, `Waker`, `Clipboard` | A driver `FnOnce(Box<dyn AppHandler>) -> Result<(), PlatformError>` passed to `App::run_on` |
| The text engine | `zgui-text` | `FontSource`, `FontMetricsSource`, `ParagraphShaper`, `GlyphRaster` | `zgui_runtime::App::with_text_engine`, `with_metrics`, `with_glyph_raster` |

- **Renderer.** A renderer with no vector rasteriser attached draws general vector items as empty
  space, with no error. See [Vello and coverage rasterisers](/docs/architecture/renderer#vello-and-coverage-rasterisers)
  and, for a host that already owns a wgpu device,
  [Adopting a host-opened device](/docs/architecture/renderer#adopting-a-host-opened-device).
- **Platform.** A platform backend does not implement `AppHandler`; it calls one.
  `zgui_runtime::Runtime` is the implementation. See
  [Drivers and backend selection](/docs/architecture/platform-layer#drivers-and-backend-selection).
- **Text engine.** The umbrella `App` does not expose the three text factories. It installs them
  from `zgui::app::Fonts`, so a face registered once serves every window. To replace the text
  engine, build with `zgui_runtime::App` directly. See [The text engine](/docs/architecture/text-engine).

### Pins that fail silently

`cargo xtask ledger versions` (`xtask/src/ledger/check/versions.rs`) enforces these, because a
wrong value produces wrong behaviour rather than a build error:

| Pin | Reason |
|---|---|
| `stylo`, `reactive_graph`, `reactive_stores`, `any_spawner` pinned to an exact patch release | A drift to another release would otherwise go unnoticed. Moving a pin is a deliberate change. |
| `reactive_graph` enables `effects` | Without it, the interface compiles and runs but never updates. |
| `reactive_graph` does not enable `nightly` | The workspace's nightly toolchain must not switch it on. |
| `cephal` has `default-features = false` and exactly `block`, `flex`, `grid` | `parallel` would add a second worker pool; zgui drives its own pool through Cephal's batching seam. Each algorithm is a formatting context the box tree dispatches to. |
| `wgpu` is 29.x, one copy in `Cargo.lock` | Vello 0.9 links wgpu 29.0.4 and shares one device, queue and target texture with the renderer. |
| `ash` has one copy in `Cargo.lock` | The console backend passes `vk::Image` to wgpu-hal; two copies would be two unrelated types. |
| `linebender_resource_handle` has one copy | It makes the text engine's and the rasteriser's font-data types the same type. |
| `skrifa` has at most two copies | The text engine and Vello are on different releases. |

## Ledger checks

`cargo xtask ledger` runs thirteen checks. Any violation fails the gate. `cargo xtask ledger <name>`
runs one check, and `cargo xtask ledger --self-test` runs every check against a fixture with a
planted violation, to prove that the check can fail.

| Check | What it asserts |
|---|---|
| `engines` | Each external engine is named only by the crates permitted to name it. |
| `unsafe` | `unsafe` is forbidden outside an allowlist, and every `unsafe impl Send`/`Sync` has a `// SAFETY:` comment. |
| `attribution` | Adapted code carries its licence header and a matching `NOTICE` row. |
| `versions` | Exact version pins, one copy of wgpu, and feature sets that fail silently. |
| `pinned` | Two crates have exact dependency lists, and no crate below the view layer names `zgui-view`. |
| `layers` | Every dependency points at the crate's own layer or a lower one. |
| `ignored` | No test is `#[ignore]`d. |
| `counters` | Every frame counter is incremented somewhere, or listed as waiting for its stage. |
| `skips` | Every counter of avoided work names its pair and has a non-vacuity test. |
| `clock` | Every wall-clock assertion lives in a target the gate runs in release mode. |
| `mutation` | A document is changed only through its batch API, never through the arena. |
| `inert` | Every enum variant that code branches on is constructed somewhere. |
| `tag-syntax` | No view, in code or docs, uses the old tag syntax. |

### `layers` check

The check reads the `# L<n> — ` header of every member manifest and compares each edge in
`[dependencies]` and `[build-dependencies]`. A member without a header fails, so a new crate cannot
skip the rule. `probe` and `xtask` are the only members with no layer.

Development dependencies are not checked. Several crates drive their own tests through a higher
layer, for example taking `zgui-testkit-scene` (L7) for golden-image comparisons. Test binaries are
not linked into a consumer's build, so these edges do not change the shipped graph.

### `pinned` check

Two crates have exact dependency lists, because other backends are substituted underneath them:

| Crate | Normal dependencies, exactly |
|---|---|
| `zgui-view` | `zgui-geom`, `zgui-interned`, `zgui-reactive`, `zgui-vocab` |
| `zgui-vocab` | `accesskit`, `zgui-geom`, `zgui-interned` |

Neither crate may see `stylo`, `stylo_dom`, `selectors`, `cephal`, `parley`, `wgpu`, `vello`,
`winit`, `zgui-dom`, `zgui-layout`, `zgui-style`, `zgui-render`, `zgui-scene` or `zgui-platform`
in any section, including development dependencies.

No crate below the view layer may depend on `zgui-view`. The check lists thirteen such crates by
name: `zgui-input`, `zgui-scroll`, `zgui-a11y`, `zgui-anim`, `zgui-edit`, `zgui-layout`,
`zgui-style`, `zgui-dom`, `zgui-text`, `zgui-paint`, `zgui-scene`, `zgui-render` and
`zgui-platform`. Event dispatch is the usual temptation: the input layer decides which listeners an
event reaches, and the view layer calls them.

### `engines` check

`xtask/src/ledger/check/engines.rs` lists, for each external engine, the crates that may name it.
Replacing or patching an engine is therefore a change to a known set of manifests.
[External dependencies](#external-dependencies) shows which crates name each engine today. Any
dependency whose name starts with `gpui` is rejected outright.

## Lints and `unsafe`

`[workspace.lints]` denies `missing_docs`, `unsafe_code` and broken intra-doc links, and warns on
`unreachable_pub`, private intra-doc links, all of clippy, and undocumented `unsafe` blocks. Every
member sets `[lints] workspace = true`.

`cargo xtask ledger unsafe` requires `#![forbid(unsafe_code)]` in every crate root outside this
allowlist:

| Crate | Allowed `unsafe` for |
|---|---|
| `zgui-arena` | Chunk initialisation that hands out address-stable references. |
| `zgui-dom` | The cell discipline and the mutation cell. |
| `zgui-geom` | Plain-old-data impls for types sent to the GPU. |
| `zgui-render-wgpu` | Loading a pipeline cache from a blob; creating a device through wgpu-hal with requested Vulkan extensions. |
| `zgui-render-vector-vello` | Creating a pipeline cache from a blob. |
| `zgui-platform-winit` | The Wayland clipboard constructor; AppKit calls for the macOS menu, reopen request and title-bar buttons. |
| `zgui-platform-wayland` | Borrowing the compositor's display and surface pointers as window handles. |
| `zgui-drm` | ioctls, mapping dumb buffers, owning dma-buf descriptors. |
| `zgui-evdev` | ioctls and reading event records from a byte buffer. |
| `zgui-xkb`, `zgui-seat`, `zgui-libinput` | Loading the library at run time and calling into it. |
| `zgui-platform-drm` | Reporting a surface's DRM handles; the Vulkan calls that create scanout images. |

Every hand-written `unsafe impl Send` or `unsafe impl Sync` needs a `// SAFETY:` comment directly
above it.

## Publishing and releases

The published crates are on crates.io at **0.1.0**, tagged `v0.1.0`. An application adds them with
`cargo add zgui` or:

```toml title="Cargo.toml"
[dependencies]
zgui = "0.1"
```

### Toolchains

- **Published crates build on stable Rust 1.90 or later.** `rust-version = "1.90"` is set in
  `[workspace.package]`. The CI job "Check stable 1.90" runs `cargo +1.90.0 check` over every
  published crate.
- **The repository is developed on a pinned nightly** (`rust-toolchain.toml`, currently
  `nightly-2026-04-16`). Miri needs nightly, and so does `zgui-xkb` in the console stack. The
  console crates do not inherit `rust-version`.

### Package contents

`[workspace.package] include` limits every package to `src/`, `build/`, `build.rs`, `README.md`,
`LICENSE` and `NOTICE`. Tests, fixtures and test fonts are not shipped. Each published crate has its
own README.

<Callout type="info">
The repository patches `fontique` (the font collection under Parley) from `vendor/fontique`, so that
a font query keeps resolved families between paragraphs. `[patch.crates-io]` applies only inside
the workspace. A crates.io build uses the released fontique: the text is the same, but font
resolution is slower. An application can opt into the patched copy:

```toml
[patch.crates-io]
fontique = { git = "https://github.com/zortax/zgui", tag = "v0.1.0" }
```
</Callout>

### One version for all crates

Every member inherits `version` from `[workspace.package]`, and all crates are released together.
`zgui 0.1.0` therefore always sits on `zgui-render 0.1.0`, and there is no compatibility matrix
between the framework's own crates.

`xtask/src/release/lockstep.rs` checks that:

- every member writes `version.workspace = true`;
- every dependency of a published crate that has a `path` also has a version requirement, whether
  it is an internal crate or an external one, and whether it is written in the member or inherited
  from the workspace;
- no published crate depends on an unpublished member, including optional and target-specific
  dependencies.

### The release gate

`cargo xtask release` runs three steps:

1. **Lockstep**, as above.
2. **Packaging.** `cargo package --workspace --locked`, excluding unpublished members, then builds
   every published crate from its package. This catches files the package leaves out and builds
   that read outside their own directory.
3. **Compatibility.** `cargo semver-checks check-release` against the newest `v*` tag that does not
   contain the checked commit. Before the first tag, it reports "no baseline" instead of passing.

`cargo xtask ci` runs the same gate but only packages the crates, without building them.

The release itself has two parts. The crates are published from a local checkout with
`cargo publish --workspace`. Pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`, which
checks that the tag is on `main` and matches the workspace version, runs the full CI workflow, and
creates the GitHub release with generated notes.

### API stability rules

- **`#[non_exhaustive]`** marks enums that are expected to grow without a breaking change: error
  enums, frame outcomes, host-hook answers, and platform enums. (A unit test in `zgui-platform`
  rejects any public enum there without it.) Enums that list the framework's own content, such as
  `PrimitiveKind`, `Batch` and `Filter` in `zgui-scene`, are exhaustive on purpose: adding a member
  must update every match in the tree.
- **Traits grow with default methods.** A method added later has a default body, so existing
  implementations keep compiling. Every method of `zgui_runtime::HostBinding` has one.
- **`#[doc(hidden)]`** hides items that exist only so one crate can reach another, such as the
  typestate markers behind required-prop errors. The macro-expansion roots stay visible.
